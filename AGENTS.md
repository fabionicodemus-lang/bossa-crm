# Bossa CRM development instructions

- Work in the existing checkout. Confirm the current branch, full HEAD, and `git status --short` before editing. Preserve other people's changes and avoid parallel edits to the same branch.
- Use Node 22 (`.nvmrc`) and `npm ci --no-audit --no-fund`. Do not use production credentials or data in tests. Keep migrations additive until they are validated against an isolated copy of the full schema; never apply them to production from an agent task.
- Commercial identity work must keep the original contact IDs, source rows, ledger events, messages and snapshots. Equal phone numbers are insufficient evidence of identity. A contact reconciliation is a reviewed alias relation, not a destructive merge or a transfer of commercial facts.
- Targeted tests: `node scripts/commercial/check-contact-reconciliation.mjs` and `node scripts/commercial/check-contact-integrity.mjs` (PGlite). For the concurrent review test, use a disposable PostgreSQL 17 database named `commercial_reconciliation_test` and run `PGHOST=127.0.0.1 PGDATABASE=commercial_reconciliation_test node scripts/commercial/check-reconciliation-concurrency.mjs` after setting its local connection variables. The test initializes its own fixture and must never point to another database.
- Test the real reconciliation server actions with `node --experimental-strip-types --loader ./scripts/commercial/reconciliation-actions-loader.mjs scripts/commercial/check-reconciliation-actions.mjs`. Where Chromium and Playwright are available, run `node --experimental-strip-types --loader ./scripts/commercial/reconciliation-actions-loader.mjs scripts/commercial/check-reconciliation-browser.mjs`. The browser test renders the actual page and submits forms to the actual actions using isolated authentication and PGlite adapters; it does not establish production authentication or full Next.js deployment behavior.
- Quick proposal status: run `node scripts/commercial/check-proposal-status.mjs`, `node --experimental-strip-types --loader ./scripts/commercial/proposal-status-route-loader.mjs scripts/commercial/check-proposal-status-route.mjs`, and `node scripts/commercial/check-proposal-status-concurrency.mjs` (uses and removes its own disposable Docker PostgreSQL 17 container). With local Chromium and Playwright, run `node scripts/commercial/check-proposal-status-browser.mjs`; this renders the real React component with an isolated PGlite RPC adapter and is not deployed Next.js authentication homologation.
- WhatsApp AI proposal detection: run `node scripts/commercial/check-ai-proposal.mjs`, `node --experimental-strip-types --loader ./scripts/commercial/ai-proposal-loader.mjs scripts/commercial/check-ai-proposal-producer.mjs`, and `node scripts/commercial/check-ai-proposal-concurrency.mjs` (self-contained disposable Docker PostgreSQL 17). These use fixture data and a stubbed OpenAI response; they do not send WhatsApp messages. Apply the additive AI detection migration before enabling this producer in a preview environment; the producer fails closed when its receipt table/RPC is absent.
- Integrated schema verification: `node scripts/commercial/check-integrated-schema.mjs` starts/removes its own network-isolated PostgreSQL 17 container, replays the repository's actual business DDL and all commercial migrations, and exercises the flows in that single database. Legacy data/backfills, Vault checks, scheduling statements and automation extensions are explicitly omitted and inventoried; Auth/Storage use the documented local adapter. JSON catalog/results/plans and a schema-only dump go to `/tmp/bossa-commercial-homologation` (override with `BOSSA_HOMOLOGATION_OUTPUT` under `/tmp` or `/workspace`). This is not certification of the deployed Supabase schema or JWT service. Review `scripts/commercial/homologation/preflight-source-scope.sql` in a sanitized complete-schema preview before promoting the scope correction; do not rewrite or silently fix existing inconsistent records.
- Before completion, run the repository's commercial, integrity, recovery and source request suites plus `npm run lint`, `npm run typecheck`, and `npm run build`. Use dummy build variables only as documented in `.github/workflows/validate.yml`; never treat them as integration credentials.
- The fixed PR #128 checklist has 24 macroitems. A partial reconciliation or an isolated fixture pass does not complete F1.5. Preserve the last verified 12/24 count unless the exact checklist and full acceptance evidence justify a change.
- Private homologation inputs, full catalog/dumps, ledger fingerprints, policies, baseline-derived SQL and detailed reports must stay outside the repository and CI artifacts. A catalog-derived export needs explicit column ACL/default ACL restoration and managed Auth/Storage prerequisites; do not call the repository adapter a full Supabase restore. Never replay historical migrations or repair a remote ledger to align filenames. Preserve the existing baseline and apply only verified pending versions once.
- Standalone permission candidates in `supabase/security/` are a separate security release, not automatically part of the commercial migration sequence. Validate before/after body hashes, argument defaults, return types, EXECUTE for PUBLIC/anon/authenticated/service_role, scoped service callers and transaction rollback in an isolated baseline before promotion. Do not schedule the legacy duplicate batch or authorize phone-only identity decisions.
- The two service-only permission candidates use SECURITY INVOKER; separately supplied batch-body corrections must preserve that mode, restricted ACL and fixed search path, reject unknown existing definitions, and avoid counting an idempotent replay as a new merge. Historical fingerprint gaps and unknown external consumers stay pending until positive evidence closes them. Private preview guards and a synthetic browser pass do not constitute human operational approval.
- Independent HTTP compatibility: `node scripts/commercial/check-http-conflict-compatibility.mjs` exercises the actual save/status RPCs before and after `supabase/compatibility/20261022_rpc_http_conflicts.sql`. Keep the original 13 migrations unchanged. This SQL contract test does not validate REST retry behavior; also verify real HTTP 409 and the rendered conflict/recovery flow in an isolated preview.
